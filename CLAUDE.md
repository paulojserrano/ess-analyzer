## Project Overview

Desktop application (local web UI + headless CLI) for analysing ASRS/ESS warehouse log data exported from the Hairobotics system. Loads one or more Excel files (one per operational day), runs a suite of Plotly analyses, and generates a self-contained HTML report with interactive charts.

## File Descriptions

**`app.py`** — Command-line entry point. No file arguments → launches the UI (`server.launch`). With files → headless run through `pipeline` (`--out`, `--analyses`, `--switch-mode`, `--switch-s`, `--pick-start`, `--no-excel`, `--browser`, `--port`).

**`pipeline.py`** — The only orchestration path (UI and CLI share it). `load_day(paths)` validates, detects and auto-configures one day (`LoadedDay`); `run_pipeline(days, RunSettings, on_progress, on_log, cancel)` runs the enabled analyses per day (modules resolved with `importlib` from `config.ANALYSIS_IMPLEMENTATIONS`), isolates failures, writes exports and the report into a timestamped run folder, and returns a `RunResult`. Analyses log through `logging`; records on the run thread are forwarded to `on_log`. Output root: `ESS_OUTPUT_DIR`, else next to the exe when frozen, else the project folder.

**`server.py` + `webui/`** — Local FastAPI app on 127.0.0.1 (single-user session state, background load/run threads, polled `/api/state`, lazy `/api/results/{day}/{idx}/figure`). `launch()` opens a pywebview window when installed, else the browser. The front end is plain HTML/CSS/JS — edit `webui/app.js` directly; Plotly.js is served from the installed plotly package.

**`exports.py`** — All Excel output. Must reuse the shared helpers (`triggergo_completions`, `extract_picks`, operational `_release_arrived_gaps`) so workbook numbers equal chart numbers.

**`config.py`** — Brand colours (`INK`, `ACCENT`), `AUTO_TYPE_PALETTE` (zone colours), `STAGE_COLORS`, `SEQ_COLORSCALE` (ordered heatmap scale — darker = more), `STAGE_LABEL_MAP` (Chinese → English stage names), `TOTAL_DURATION_COL`, `AMR_DELIVERY_TYPE_HINT`, `ANALYSIS_MODULES` (ordered registry of `(key, label)` tuples), `ANALYSIS_IMPLEMENTATIONS` (key → module path), `LIFECYCLE_ONLY`, `CHART_DISPLAY_ORDER`.

**`data_loader.py`** — Sheet detection by column-signature matching (`callback`, `station`, `lifecycle`, `efficiency`). Rows are dated per sheet with `row_timestamps(df, key)` (lifecycle: completion time first — never rely on the often-blank `创建时间`). Auto-detects LABOR station layout (`_auto_station_config` — real `LABOR-N` names from the callback sheet's point→位置类型 mapping when one-to-one, else coordinate order), lifecycle stage columns (`_auto_stage_config`), AMR robot type (`_detect_amr_type`). `build_config()` returns the runtime `cfg` dict, merging auto-detection with user overrides from `asrs_config.json`. Also: `filter_to_peak_day()`, `detect_data_date()`, `load_user_config()`.

**`report_builder.py`** — `generate_html_report(outdir, days, summary_registry)`. Builds a single self-contained HTML file with Plotly.js from CDN. Multi-day runs get a tab bar (Summary + one tab per day). Each chart is a card with title, source, method metadata, and embedded Plotly div. Chart resizing is handled on tab switch via JS.

**`analyses/__init__.py`** — Documents the `ChartResult` schema. Every `run()` must return a list of dicts with keys: `id`, `title`, `figure`, `source`, `method`, `export_hint`.

**`analyses/cycle_time.py`** — Requires the `lifecycle` sheet. Internal helpers prefixed with `_` handle each sub-chart. Uses Pearson + Spearman correlation for demand-vs-cycle scatter; demand counts prefer station-sheet triggerGo (same definition as throughput) with a callback fallback.

**`analyses/fleet_utilization.py`** — Instantaneous queue depth via sorted-array sweep-line (O(n log n)), fleet utilisation time-series, and a Little's-law WIP consistency check.

**`analyses/summary.py`** — Called with `all_days: list[dict]` (not the standard `run(data, cfg)` signature). Only invoked when ≥2 days are loaded.

**Shared cross-module helpers** (import these instead of re-implementing):
- `_common.triggergo_completions(lsr, cfg)` — THE completion definition (delivery-AMR `triggerGo` at a mapped station); used by throughput, summary, data_quality, exports, KPIs. Never count callback `complete` as completions — it fires at robot arrival.
- `_common.station_events(lsr, cfg)` — station rows with coerced `ts` and mapped `station`, AMR-filtered.
- `dwell_time.extract_picks(lsr, cfg)` — pick pairing (start-event → triggerGo) with the station-match guard; used by throughput, summary, data_quality. The start event is `cfg["pick_start_event"]`: `"arrived"` (default) or `"ppReady"` (fallback for exports missing `arrived` events — station comes from the triggerGo since ppReady locations are blank; confirmed in the GUI RUN card before running).
- `dwell_time._clipped_occupancy(...)` — hour-boundary-clipped seconds-in-use; used by throughput, switch_time.
- `switch_time.operational_switch_by_station(lsr, point2ws)` — measured per-station median switch (gaps ≤ `MAX_OPERATIONAL_SWITCH_S`); replaces the old fixed 6 s assumption everywhere (fallback `SWITCH_S_FALLBACK`, both in `config.py`).
- `fleet_utilization._delivery_leg_col(tlc, cfg)` — delivery-leg column detection; used by retrieval, robot_performance.

**Statistical conventions**: duration medians/averages are computed on full event durations attributed to the start hour (never on hour-sliced segments — slicing is only valid for occupancy sums); stage composition charts use means (additive), not medians; release→arrived gaps longer than `MAX_OPERATIONAL_SWITCH_S` are starvation, not switch time, and never count as station occupancy.

## Development Rules

### Context Awareness — Which file to touch

| Task type | File |
|---|---|
| Brand colours, stage label map, module registry | `config.py` |
| New analysis module | `analyses/<name>.py` + register in `config.py` `ANALYSIS_MODULES` |
| Chart visual changes (layout, colours, annotations) | The specific `analyses/*.py` module |
| Report HTML/CSS structure | `report_builder.py` |
| Excel sheet detection or column mapping | `data_loader.py` |
| UI layout, pages, interactions | `webui/app.js`, `webui/app.css` |
| UI API endpoints, run/load threading | `server.py` |
| Run orchestration, output folders, KPIs | `pipeline.py` |
| Excel workbooks | `exports.py` |
| CLI options | `app.py` |
| Cross-day summary charts | `analyses/summary.py` |
| Regenerate AI context index | Run `python ai_codex.py` |

### Adding a New Analysis Module

1. Create `analyses/<name>.py` — export `run(data: dict, cfg: dict) -> list[dict]`
2. Every returned dict must include all six `ChartResult` keys
3. Register in `config.py` → `ANALYSIS_MODULES` (order + label) and `ANALYSIS_IMPLEMENTATIONS` (module path); add a preflight rule in `data_loader._analysis_status` if it has data requirements
4. Add the module to the parametrised checks in `tests/test_analyses.py` if it needs special handling (all registered modules are exercised automatically)
5. If the module requires the `lifecycle` sheet, guard with `if 'lifecycle' not in data: return []`
6. Run `python ai_codex.py` to update `.ai-codex/analyses-index.md`, then `python -m pytest -q`

### Hard Rules

- **NEVER import an analysis module directly in `app.py`, `server.py` or `pipeline.py`** — `pipeline.resolve_module(key)` imports them via `config.ANALYSIS_IMPLEMENTATIONS`. (PyInstaller picks them up from `ESS_Analyzer.spec`, which lists `analyses/*.py`.)
- **NEVER mutate the `data` dict** inside an analysis module. It is shared across all analyses for a given day.
- **NEVER use `print()` for user-facing output in analysis modules** — use `logging.getLogger(__name__)` (warnings reach the run log in the UI/CLI) or raise an exception (the pipeline records it as a failed analysis and keeps going).
- **Heatmaps**: never clip `z` to the colour range (hover must show true values) — set `zmin`/`zmax` instead.
- **ALL column name strings are Chinese** — copy exact strings from `.ai-codex/data-schema.md`. Do not guess romanised versions.
- **cfg dict keys** — use only the documented keys from `.ai-codex/data-schema.md`. Do not add ad-hoc keys to cfg inside an analysis module.
- **ChartResult `id` must be unique** across all modules — use `snake_case`, prefixed by module name (e.g. `throughput_total`, `cycle_histogram`).
- **Plotly figures must be created with `go.Figure()`** — do not use `px.*` unless you verify the output is a `go.Figure` instance (report_builder calls `fig.to_html(full_html=False)`).

### Execution & Efficiency

- Use `.ai-codex/analyses-index.md` to identify which module owns a chart ID before opening any file.
- Use `.ai-codex/data-schema.md` to look up column names and cfg keys — do not grep the source for Chinese strings.
- Analysis modules are independent — changes to one do not affect others.

## Analysis Pipeline

Execution order = `config.ANALYSIS_MODULES` order (run by `pipeline.run_pipeline`):

```
throughput → dwell_time → switch_time → station_readiness → [cycle_time, disabled]
→ backlog → retrieval → fleet_utilization → robot_performance → return_flow
→ efficiency → data_quality
```

`summary` runs after all day-level analyses if `len(days) >= 2`.

Steps in `config.LIFECYCLE_ONLY` (`cycle`, `retrieval`, `backlog`) are skipped
when the `lifecycle` sheet is absent. All other modules guard internally and
return `[]` when their inputs are missing (e.g. `efficiency` without the
efficiency sheet, `station_readiness` without ppReady events).

## Data Flow

```
Excel file(s)
    └─► data_loader.load_data()        # sheet detection → {callback, station, lifecycle, efficiency}
    └─► data_loader.build_config()     # auto-detect + asrs_config.json merge → cfg dict
            │
            ▼
    pipeline.run_pipeline() [UI: background thread · CLI: main thread]
            │  per day:
            │  ├─ filter_to_peak_day()
            │  ├─ analyses/throughput.run(data, cfg)   → list[ChartResult]
            │  ├─ analyses/dwell_time.run(data, cfg)   → list[ChartResult]
            │  ├─ ... (in order)
            │  └─ collect all ChartResult dicts
            │
            ▼
    exports.save_day_exports / save_chart_data / save_combined_workbook
    report_builder.generate_html_report(run_dir, days, summary_registry)
            └─► asrs_analysis_output/{YYYY-MM-DD_HHMMSS}/asrs_analysis_report.html
```

## ChartResult Schema

Every analysis module's `run()` must return a list of dicts conforming to:

```python
{
    "id":          str,        # unique snake_case identifier, e.g. "throughput_total"
    "title":       str,        # human-readable chart title
    "figure":      go.Figure,  # Plotly figure — must support .to_html(full_html=False)
    "source":      str,        # sheet(s) used, e.g. "callback sheet"
    "method":      str,        # one-sentence computation description
    "export_hint": str,        # associated Excel filename, or "" if none
}
```

## User Config Override

Place `asrs_config.json` in the same directory as the `.xlsx` file:

```json
{
    "station_types":  { "LABOR-1": "Zone A" },
    "design_rates":   { "LABOR-1": 120 },
    "type_colors":    { "Zone A": "#ff6b6b" },
    "amr_type":       "K50"
}
```

`data_loader.load_user_config()` merges this over auto-detected values.

- Not all sheets are present in every file. The `lifecycle` sheet is optional — modules that need it guard with `if 'lifecycle' not in data`.

- Robot types: `K50` (shuttle/delivery robot), `A42` (storage retrieval robot).
- Location patterns: `LABOR-N` = workstation, `LA_SHELF_STORAGE` = storage shelf, `LT_LABOR:POINT:X:Y` = station queue point, `HAI-XXX-XXX-XX_N` = storage grid position.
